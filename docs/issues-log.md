# Issues log — what went wrong with DevConnect / DevCommand, and how we fixed it

These are the main problems I ran into while building the Mizuho America site with DevConnect (the WordPress plugin) and
DevCommand (the Claude Code agents). For each one: what happened, how I found it, why it happened, and what I did about it.

---

## 1. Accuracy: the page conversions came out wrong or not editable

### Elementor pages came out as code boxes
**What happened.** I gave DevConnect the page HTML and asked for an Elementor page. Instead of real headings, text, images and
buttons, it wrapped everything in "HTML widgets", which are just boxes of raw code. About Us came out as 7 code boxes. Contact Us came
out as a single box for the whole page, and the contact form inside it could not send anything.

**How I found it.** The page looked roughly right in the browser, so I counted the widget types in what DevConnect produced: all of
them were HTML widgets, and there wasn't a single heading or image widget. An editor opening the page would only see code.

**Why it happened.** DevConnect's HTML converter only understands simple text and image patterns. Anything more complex (a form, an
accordion, a multi-column layout) falls back to "put the HTML in a code box".

**How I fixed it.** I rebuilt both pages with real Elementor widgets, generated by a script from the design so it can be repeated.
Contact Us now uses Elementor's own Form widget (it really submits and saves entries) and an accordion for the FAQ. The phone, email
and address are linked to Site Settings, so they come from one place. Every text and image is now editable in the Elementor editor.

### The ACF conversion merged and lost sections
**What happened.** Before building the ACF fields, DevCommand cuts every page into sections (one section = one ACF layout).
On **Resources** (5 sections) it **merged Testimonials and Brochures** into one small unnamed block (`02-pos-02`, 2 KB instead of
14 KB + 37 KB), so the Brochures section disappeared. On the **product pages** it **dropped four sections**: Accessories and
Related products on all three products, plus Instruments included (Variation A) and Size guide (Variation B). Those layouts would
never have been created.

**How I found it.** I listed the sections I expected from reading every page myself and compared them with what the converter
produced: Resources came out as intro, one unnamed block, fast facts, continue-your-visit; the Sugita product came out with only
overview and testimonial.

**Why it happened.** The splitter has a rule that closes an open list item (`<li>`) as soon as another block starts inside it.
Browsers only do that for paragraphs. Our cards are list items with blocks inside, so the splitter thought the section had ended
early and swallowed the next one.

**How I fixed it.** I ran a copy of DevCommand's splitter with that rule limited to paragraphs (the plugin file itself is untouched,
so the bug can be reproduced and reported) and re-ran the conversion. Every section came through: 33 sections across the pages,
each one an exact piece of its page. Proof: the broken output in `docs/evidence/flow-a/conversion/slicer-bug/`, the correct output
in `spec/fragments/`.

### Pixel-perfect, but it broke when the text changed
**What happened.** The desktop layouts matched the design exactly, but they were built by pinning every item to a fixed position,
like stickers on a board. With the design's text it looked perfect. If an editor wrote a longer heading, it did not push the content
below it down; it just ran over it.

**How I found it.** I made test pages where every heading was doubled. All my automated checks passed, because they only looked for
things sticking out sideways. It was only when I looked at the screenshots that I saw the headings overlapping the cards and text below.

**Why it happened.** The generated CSS copied Figma's exact coordinates (`position: absolute` at a fixed top/left) instead of letting
elements flow one after another.

**How I fixed it.** I wrote a script that measures where every item sits and rebuilds each layout as rows. Each row stays exactly
where the design puts it, but it can grow when its content grows and push the rows below it down. The real pages still match the
design pixel for pixel, and the long-text test pages now look clean. Buttons and labels with fixed sizes can now wrap onto two lines
instead of spilling out.

## 2. It says "success" when nothing happened (the most dangerous one)

### The field-group tool dropped the fields
**What happened.** I used `dev/acf-manage-field-groups` to create the Site Settings field group with 26 fields. It said "ok", but the
group was saved with **zero** fields. Flexible Content layouts were dropped the same way.

**How I found it.** I didn't trust the "ok". I opened the saved file and the database: the group existed, but there was nothing in it.

**Why it happened.** The tool only saves the group itself and never saves the fields inside it, and it throws away settings it
doesn't recognise, such as Flexible Content layouts.

**How I fixed it.** I stopped using that tool to create fields. All field groups are written as ACF JSON files in the theme (which ACF
loads directly), and the tool is only used afterwards to read them back and check.

### The page-build tool dropped parts of the page
**What happened.** I used `dev/build-page` to save the header and footer. It said "ok", but it kept only 1 part of the page out of 20
(header) and 29 (footer). For about three minutes the whole site had an empty header and footer.

**How I found it.** The reply said it had saved 1 node, while I had sent 20 and 29, so I counted what was actually stored.

**Why it happened.** The tool expects DevConnect's own page format. I sent it a normal Elementor page, and instead of giving an error
it silently dropped everything it didn't understand.

**How I fixed it.** Elementor pages are now saved with `dev-connect/elementor-set-page-data`, which accepts normal Elementor data, and
after every save I count the stored parts to make sure nothing is missing.

### Saves that were never stored
**What happened.** `dev/acf-read-write-values` reported success on writes that ACF then ignored. On every ACF page the section settings
(section id and "hide section") were never saved; on Home, the quote and stats showed raw `<br>` code; on the three product pages the
buttons came out empty.

**How I found it.** The front end was missing things the tool said it had saved, so I read every value back from WordPress and
compared it with what I had sent.

**Why it happened.** ACF silently ignores data in a shape it doesn't expect (a nested object for a "clone" field, two fields sharing
one name), and the tool never checks whether anything was actually stored.

**How I fixed it.** I fixed the shape of the data (flattened the clone fields, turned `<br>` into real line breaks, renamed the clashing
field) and made my content script read every value back after writing it, so a silent skip gets caught straight away.

### The Elementor page kept showing the old version
**What happened.** When I saved the rebuilt About Us page with `dev-connect/elementor-set-page-data`, it reported success and all 191
parts were stored, but the live page kept showing the old code-box version.

**How I found it.** The database had the new page, the browser still showed the old one.

**Why it happened.** Elementor keeps a cached copy of each page. Saving in the Elementor editor clears it; this tool doesn't, even
though its description says it regenerates the CSS.

**How I fixed it.** After every Elementor write I delete the page's cache entry (`_elementor_element_cache`) and flush Elementor's CSS.
It's built into the publish script. This should really be done by the tool automatically.

## 3. Its own validators can't be trusted

**What happened.** DevConnect's conversion validator reported "valid, no issues" on the About Us page that was made entirely of code
boxes. DevCommand's coverage checker did the opposite: it flagged the product and resource field groups as "missing layouts" when
nothing was missing (those groups simply aren't Flexible Content).

**How I found it.** In both cases what I saw on the page didn't match what the checker said.

**Why it happened.** The validators check the structure of the data (is it well-formed?), not whether the result is actually good or
editable, and the coverage checker assumes every field group is a page-sections group.

**How I fixed it.** I stopped treating a green check as proof. Every step was verified by reading values back from WordPress,
counting what was stored, comparing each section with the design, and looking at the screenshots myself.

## 4. The pipeline steps don't fit together

**What happened.** DevCommand's deploy step couldn't read the content files that its own previous step (the theme assembler) had just
produced. Its media step crashed, and its page and content steps planned zero writes.

**How I found it.** A dry run of the deploy showed nothing would be written.

**Why it happened.** The two steps expect different file formats for the same data, and the deploy step has no support for custom
post types (our products and resources).

**How I fixed it.** I wrote my own script (`tools/seed_acf.py`) that takes the same content files and pushes them through DevConnect:
images, 23 products, 47 resources, categories, page sections and Site Settings, reading every value back at the end.

## 5. Quirks and bugs in the tools themselves

- **Empty inputs are rejected.** Tools that take no inputs refuse the empty `{}` they're supposed to receive. **Workaround:** send a
  dummy value (`{"_": 1}`) when the tool allows it, or a real optional parameter.
- **A setting saved in the wrong place.** `dev/elementor-update-page-settings` reported that it had changed the About Us page template,
  but it saved the value inside Elementor's settings instead of WordPress's page template. The page kept the default template.
  **Found** by checking the page's body class. **Fixed** by setting the template directly with WP-CLI.
- **A read is treated like a write.** Just reading all fields of a post made DevConnect take a database backup and add an audit entry
  every time, which clutters the backups and the audit log. **Workaround:** keep reads to what's needed and be aware of it when reading
  the audit log.
- **Connecting on Windows needed fixes.** DevConnect needed a Windows-specific patch, and the MCP connection needed a path-case fix
  before Claude Code could talk to the site at all.

## 6. The AI agents cut corners

- **Text copied from a screenshot.** One planning agent typed the page copy by reading the screenshot instead of taking it from the
  Figma file, which introduced small wording mistakes. **Found** by comparing the text with the Figma data. **Fixed** by re-running it to
  take every string from Figma.
- **Its own compiler instead of the real one.** Another agent quietly wrote its own HTML compiler instead of using DevCommand's, so its
  output didn't follow DevCommand's rules (the real validator reported 69 violations). **Found** by reading the files it created.
  **Fixed** by re-planning against DevCommand's real recipes and compiler.
- **Stalls and usage limits.** Some agent runs stalled or stopped halfway when they hit usage limits. **Fixed** by resuming from the
  last saved step and checking what had and hadn't been done before continuing.

## 7. It's fragile to the environment

**What happened.** After the computer rebooted, the connection to DevConnect just failed with "connection refused", and every tool
stopped working, with no hint about why.

**How I found it.** The site itself didn't load either, and none of the site's services (web server, PHP, database) were running,
even though the Local app was open.

**Why it happened.** Local doesn't restart sites after a reboot, and DevConnect lives on the site, so when the site is down every
tool fails in the same unhelpful way.

**How I fixed it.** I started the site through Local's own API (the same thing its "Start site" button does), restarted the local
preview server, and continued. On the same machine, Git Bash had also been quietly turning `/%postname%/` into a Windows path when
setting permalinks, which broke category pages and some links. I fixed the WP-CLI wrapper so it can't happen again and reset the
permalinks.

---

## Takeaway

DevConnect and DevCommand save a lot of time, but they can't be trusted on their own. They often report success when they didn't
do the job, so every step has to be checked by reading the data back and looking at the page.
